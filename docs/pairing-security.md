# 配对与安全边界

## 权限说明

官方 Vehicle Command 协议是参考；yoziru/tesla-ble 是第三方 C++ 实现，不是 Tesla 官方库。已检查的参考版本包含 Vehicle::unlock() 与 Vehicle::pair(role)，pair 的默认值是 Owner，因此必须显式传 Keys_Role_ROLE_DRIVER。

**Driver 不是仅 Unlock 的硬件权限。** 应用白名单只能限制本软件发出的动作，不能证明窃取私钥后无法执行其他车辆动作。设备留车内是否影响车辆启动授权，必须按车型与钥匙行为实测；“软件没有启动接口”不能代替此项验证。若不能满足“不提供驾驶授权”的要求，应停止启用或重新评估授权方案。

## 后续现场配对流程（首版未实现配对工具）

1. 核对车辆支持本地 BLE 钥匙及对应车机版本；准备现有合法 NFC 卡和备用钥匙。
2. 在设备本地生成独立密钥。禁止复用车主手机钥匙、提交 PEM、聊天传输私钥。
3. 进入物理配对模式；只允许停车现场操作，禁止远程自动配对。
4. 初始化安全存储，再建立车辆 BLE 连接与通知订阅，显式调用 pair(ROLE_DRIVER)。
5. 按车辆屏幕提示使用合法钥匙卡确认。不能假设所有车型/版本的提示完全一致。
6. 读取并核对车辆钥匙列表、角色及设备标识。配对请求已发送不等于授权成功。
7. 首先手动单次 Unlock 测试，确认应答/门锁状态以及独立启动授权。随后才接人脸触发。
8. 丢失、转卖或异常时，从车机删除此设备钥匙，并清除本地密钥/人脸模板；保留可用备用钥匙。

## 真实接入的门槛

- 应用只暴露 unlock，无任意 protobuf、命令透传、启动/驾驶动作。
- 安全启动、Flash/NVS 加密与调试口策略必须结合量产/开发恢复计划制定。不可在首次调试中盲目烧录不可逆 eFuse。
- 普通 NVS 不是安全密钥库。硬件安全元件候选要先验证协议库是否支持外置签名，不能只采购元件就宣称密钥不可导出。
- 视觉节点与主控之间使用带随机挑战、会话有效期和消息认证的通道；attempt 计数不能抵御重启重放或恶意串口注入。
- BLE 会话、计数器和持久化错误必须 fail closed。协议请求已排队不是成功；未知结果不自动重发。
- 物理急停独立切断补光和执行允许；软件急停仅为补充。
